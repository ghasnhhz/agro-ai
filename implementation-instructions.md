# Implementation Instructions

The project documentation has already been created (`requirements.md` and `todo.md`).

Your job now is to implement the project.

## Development Rules

1. Read and follow `requirements.md`.
2. Use `todo.md` as the source of truth.
3. Complete tasks one by one.
4. After completing each task:

   * Mark it as completed in `todo.md`
   * Commit the changes
   * Push the feature branch to GitHub
   * Create a pull request
   * Merge into `main`
5. Then create the next feature branch and continue.

---

## Git Workflow

Use feature-based development.

Recommended branches:

* `feature/project-setup`
* `feature/database`
* `feature/land-profitability`
* `feature/disease-detection`
* `feature/land-marketplace`
* `feature/deployment`

For every feature:

1. Create feature branch.
2. Implement feature.
3. Commit changes with meaningful commit messages.
4. Push branch to GitHub.
5. Create pull request.
6. Merge into `main`.
7. Update `todo.md`.
8. Create next feature branch.

## Development Priorities

This is a hackathon project.

Prioritize:

1. Fast implementation
2. Working MVP
3. Clean user experience
4. Demo readiness
5. Real-world usefulness

Avoid:

* Overengineering
* Complex architectures
* Premature optimization

---

## MVP Strategy

Build the smallest version that demonstrates value.

If a feature would require multiple days of work:

* Create a realistic simplified implementation.
* Preserve the user experience.
* Focus on demonstrating the concept.

The goal is to impress judges with a working product, not a perfect production system.

---

## Progress Tracking

`todo.md` is the single source of truth.

Requirements:

* Update it after every completed task.
* Keep task status accurate.
* Never skip progress updates.

---

## Execution Plan

Start with:

1. Connecting to the GitHub repository.
2. Creating the project structure.
3. Completing the first unchecked task in `todo.md`.

Continue autonomously until all MVP tasks are completed.

If a requirement is unclear:

* Make the most reasonable MVP decision.
* Document the decision.
* Continue implementation.

Do not stop unless blocked by missing credentials, API keys, or external access requirements.
